文: {text}"""

   def ask(text):
       payload = {"model": MODEL, "stream": False, "messages": [
           {"role": "user", "content": PROMPT.replace("{text}", text)}]}
       req = urllib.request.Request(
           OLLAMA_URL, data=json.dumps(payload).encode("utf-8"),
           headers={"Content-Type": "application/json"})
       with urllib.request.urlopen(req) as res:
           return json.load(res)["message"]["content"]


   # ---------- 受け取り方1: 厳格 ----------

   def strict_json(raw):
       """返ってきた文字列がそのままJSONであることを要求する。

       仕様どおりではあるが、仕様どおりに返すかはモデル次第で、こちらに決定権がない。
       """
       return json.loads(raw)


   # ---------- 受け取り方2: 緩い ----------

   def loose_parse(raw):
       """前置き・コードフェンス・末尾コンマを許して、中の対応表を取り出す。

       こちらのコードは自分で直せるが、モデルの癖は直せない。
       """
       s = raw.strip()
       s = re.sub(r"^```(?:json)?\s*|\s*```$", "", s, flags=re.S)  # フェンスを剥がす
       m = re.search(r"\{.*\}", s, re.S)                            # 最初の { から } まで

       body = re.sub(r",\s*([}\]])", r"\1", m.group(0))             # 末尾コンマを落とす
       return json.loads(body)

       全部一致だけを見ると「惜しい失敗」と「全然違う失敗」が同じ0点になるため。"""
       return sum(1 for k in want if str(got.get(k, "")).strip() == want[k])

続いて `loose_parse` を使って緩やかに受け止める方法を試す。こちらのコードは正規表現で```jsonや```のフェンスを剥がし、最初の `{` から `}` までを抽出して末尾のコンマを除去した上でJSONとして読み込む。素材から貼り付けたこの関数は、モデルが付け加えた前置きやコードフェンス、末尾のコンマを許容し、中身の対応表だけを取り出す仕組みだ。実測ログでは5件すべて `3/3` で受理され、厳格な場合の `2/5 件` と比べてすべてのデータが正しく取り出せている。これは「モデルを直す」のではなく「受け取り方を広げる」アプローチの有効性を示している。
## 評価セットを作る
評価に必要な正解データ `EVALSET` と、モデルの出力と比較して何項目一致したかを数える `score` 関数を素材から貼り付けた。5文の正解データをリスト化し、それぞれのモデル出力と照らし合わせて `name` `place` `date` の3項目が何個合っているかを数える仕組みだ。全部一致だけを見ると「惜しい失敗」と「全然違う失敗」が同じ0点になってしまうため、部分点を出して傾向を把握する。機械採点によって、モデルがどの項目を間違えやすいか、あるいはどの程度の精度で抽出できているかを定量的に見ることができる。
## 実験：厳格 対 緩い
素材2のログをそのまま引用すると、以下の結果となる。厳格 `strict_json` の場合、モデルが```jsonで始まり改行が入っているため最初の3件で `JSONDecodeError` により拒否され、2/5 件の受理にとどまり合計 6/15 点。一方、緩い `loose_parse` ではフェンスの削除とコンマの除去により5/5 件すべて `3/3` で正しく受理され、合計 15/15 点となった。この差は、受け取り側が「モデルの出力形式を厳密に要求するか緩やかに許容するか」によって、得られる評価値が大きく変わることを示している。実測ログにある「生の返答」の先頭2件はどちらも```json```で始まり、中身はほぼ期待通りの構造をしていたが、厳格側では1文字の差や余分な記号ですぐに弾かれるのに対し、緩い側ではそれを吸収して正しく評価できている。
## まとめ
- 小型モデルは「JSONで返して」と even お願いしても、形式に前置き・フェンス・末尾コンマがつくことが多い
- 厳格な受け取りでは `json.loads` 直前の文字形が崩れると即座にエラーとなり、評価が進まない
- 緩やかな受け取りでは正規表準でフェンスとコンマを除去し、中身だけを抽出することですべての評価項目を正しく取り出せる
- 評価セットを用いて機械採点する場合、部分点を出すことで「惜しい失敗」と「全然違う失敗」を使い分けられる
- 受け取り側の工夫が、モデルの癖を無視したデータ抽出の精度を決める重要な要素となる
- 今後の課題として、モデルごとの出力癖をどう自動的に吸収する受け取りルールにするかが挙げられる
## 練習問題
1.  モデルに「JSONだけを返して」と頼んだときに、```が付いた出力を人間が読む際に意識することは何か、理由を説明せよ。
2.  `strict_json` で `JSONDecodeError` が発生する主な原因を2つ挙げよ。
3.  `loose_parse` で文字列からJSONを抽出する手順を、コードの行番号を添えて3つの手順に分けて説明せよ。
4.  評価セットでの機械採点において、3項目中2項目が一致した場合のスコアは何点か。その判断基準を簡潔に述べよ。
5.  本講座で扱う小型モデルの出力形式に対応するため、受け取り側のコードに追加しておくと望ましい機能を1つ挙げ、その理由を添えよ。

### 解答例
1. ```が付くとモデルがコードブロックとして出力していると認識しやすく、人間は中身のJSON部分だけを探せばよいが、プログラムがそれを無視して全体をパースしようとするとエラーになるため、形式の前処理が必要となるからだ。
2. モデルが出力する文字列に```jsonや改行、あるいは `name: "太郎"` のようにキーと値の前に余分な空白や記号が含まれていること、また `{` から `}` までの範囲に含まれない文字が混ざっていることが主な原因となる。
3. まず正規表現で```jsonや```のコードフェンスを文字列の先頭と末尾から剥がす。次に正規表現で `{` から始まり `}` で終わる部分を抽出し、抽出した文字列の末尾にあるコンマを削除する。最後に `json.loads` で文字列をJSONオブジェクトに変換する。
4. 3項目中2項目が一致すれば `2` 点となる。`score` 関数は `want` の各キーについて `got.get(k, "")` で取り出した値と一致すれば1点加算し、全部で3点満点の内から何点取れたかを返す仕組みだからだ。
5. モデルごとの出力癖（例：必ず ``` で始まる、あるいは必ず末尾にコンマが付く）を検知して自動で除去する正規表現ルールを1つ追加しておくと、以後の実験で `strict_json` によるエラーを大幅に減らせるため。実際のログでも `loose_parse` を導入したところ受理率が5/5 から 2/5 に改善するなど、形式への対応がスコアに直結するからだ。
